**핵심 분기 로직** (`wikiEditStore.ts`의 `submitEdit`):

```
isDelete = isEmptyBody(제출 본문)
wasEmpty = isEmptyBody(현재 실제 값)   // 저장 시점에 서버가 새로 읽음
accept      = isAdmin || (!isDelete && isAdditionOnly(현재 실제 값, 제출 본문))
acceptedVia = !accept ? null : isAdmin ? "admin" : wasEmpty ? "empty_section" : "addition_only"
```

**기준은 "섹션이 비었는가"가 아니라 "이 편집이 지우는 글자가 있는가"다** (2026-09-04
개정, WIKI_MODEL.md "편집에는 두 갈래가 있다"). 남의 글을 그대로 두고 덧붙이기만 하면
이미 쓰인 섹션이라도 즉시 반영된다. 공백·줄바꿈만 달라진 것은 지운 것으로 세지 않는다.

`isAdditionOnly`는 편집 화면의 빨간 형광펜과 **같은 함수**다. 둘이 갈리면 화면에
초록만 보이는데 대기열로 가는 일이 생기므로, `wikiDiff.ts`를 고칠 때는 양쪽 영향을
함께 본다.

관리자 본인 편집은 삭제라도 즉시 반영된다(자기 글을 자기가 검토하지 않음). 빈 본문
제출은 섹션 전체를 지우는 것이라 항상 검토 대기다(FR-26).

동시 제출 경쟁은 **`wiki_docs.revision`을 먼저 올려 문서를 쥐는 방식**으로 막는다.
`UPDATE ... WHERE revision = 읽은 값`이 0건이면 그 사이 누군가 반영했다는 뜻이므로,
바뀐 본문을 다시 읽어 다시 판정한다(세 번까지). 앞사람 글을 지우게 되는 편집이라면
그제야 검토 대기로 간다.

**되돌리기(FR-30)는 문서 전체가 아니라 섹션별로 재구성한다** —
`wiki_edits.revision`이 섹션 하나가 바뀔 때마다 1씩 오르는 카운터라 문서 전체
스냅샷 번호가 아니기 때문이다. 되돌리기 한 번이 여러 개의 새 리비전 번호를 만들 수
있다 — 의도된 동작이다.

**마크다운 지원 확정** (PRD 15 미결정 5번 해소). 섹션 본문 최대 4,000자, 편집 요약
선택 입력 최대 80자, 시간당 제출 상한 10건(미결정 6·7번 해소)으로 정했다.
`markdown-to-jsx`를 `disableParsingRawHTML: true` + href `http(s)` 화이트리스트로
써서 `dangerouslySetInnerHTML`을 전혀 쓰지 않는다 — 스모크 테스트로 `<script>`,
`onerror`, `javascript:`, `data:` 벡터가 무해하게 렌더됨을 확인했다.

**검증한 것.** 타입체크·린트·`next build`·`opennextjs-cloudflare build` 통과.
로컬 D1에 실제 SQL을 재현해 분기·원자성·되돌리기 재구성·제출 제한 카운트를
직접 확인했다. Auth.js JWT를 로컬에서 직접 서명해(`@auth/core/jwt`의 `encode`,
`AUTH_SECRET` 사용) 회원/관리자 세션 쿠키를 만들고, 서버 사이드 게이팅
(`/admin`·`/my/edits` 리다이렉트·404)과 FR-24 안내 문구가 역할·섹션 상태에 따라
정확히 갈리는 것을 실제 HTTP 요청으로 확인했다.

**검증하지 못한 것 — 다음에 브라우저로 직접 확인할 것.** 실제 구글·카카오 OAuth
로그인 상태에서 편집 저장 → 즉시반영/검토대기 화면 전환, 검토 승인·거절 버튼 클릭,
되돌리기 2단계 확인 UI, 대기열·최근변경·역사 화면의 실제 클릭 흐름은 이 세션에서
브라우저 확장이 연결되지 않아 눈으로 보지 못했다. 서버 로직과 데이터 계층은
검증했지만, React 폼 제출 → 서버 액션 호출의 실제 클릭 경험은 미확인이다.

**3단계 결론 (2026-09-03, 로그인).** Auth.js(next-auth v5) 공식 D1 어댑터는 이 스택
(`@opennextjs/cloudflare` + Cloudflare Workers)에서 알려진 버그가 있다
(`opennextjs/opennextjs-cloudflare#435` — 로컬 개발 중 D1 어댑터가 세션·계정을 저장하려
할 때 `getCloudflareContext` 관련 500 에러). 그래서 Adapter 인터페이스는 쓰지 않고,
**JWT 세션 전략** + `jwt` 콜백에서 [`src/lib/userStore.ts`](../src/lib/userStore.ts)로
D1에 직접 upsert하는 방식으로 우회했다. `src/auth.ts`가 설정 전체를 담고 있다.

**같은 사람이 구글·카카오 각각으로 로그인하면 서로 다른 계정이 된다** — `WIKI_MODEL.md`가
정한 대로이고 이번 구현도 그대로 따랐다. 자동 병합은 하지 않는다.

**시크릿 관리.** 로컬은 `.dev.vars`(gitignore 대상, `.dev.vars.example`을 복사해 채운다),
운영은 `npx wrangler secret put <NAME>`으로 등록한다(`AUTH_SECRET`,
`AUTH_GOOGLE_ID`/`SECRET`, `AUTH_KAKAO_ID`/`SECRET` 5개). 값은 저장소에 커밋하지 않는다.

**관리자 승격은 아직 화면이 없다.** `users.role`을 `admin`으로 올리려면 지금은 수동으로
직접 실행해야 한다 (FR-34 관리자 접근 제어 화면이 붙기 전까지의 임시 절차).

```bash
npx wrangler d1 execute kkaenam-gg --remote --command \
  "UPDATE users SET role='admin' WHERE id='...';"
```

> **즉시 반영 판정은 서버에서** 한다(`submitEdit`이 저장 시점에 실제 값을 다시 읽어
> `isAdditionOnly`로 비교한다). 지운 것이 없으면 바로 반영되고, 지우거나 고쳤으면
> 검토를 거치며, 섹션을 비우는 편집은 언제나 검토 대기다. PRD 5.4.1과 10장,
> WIKI_MODEL.md대로 구현했다.

> 즉시 반영 경로의 안전장치인 **최근 변경 화면, 한 번에 되돌리기, 제출 수 제한**
> 셋 다 구현했다(2.1 참고). 실제 서비스에 배포하기 전에 셋이 모두 동작하는지
> 다시 한 번 확인할 것. **판정 기준을 바꾸면서 즉시 반영되는 면이 크게 넓어졌다** —

| 항목 | 값 |
| --- | --- |
| 섹션 내용 최대 길이 | 4,000자 (`MAX_BODY_LENGTH`, `src/data/wiki.ts`) |
| 편집 요약 | 선택 입력, 최대 80자 (`MAX_SUMMARY_LENGTH`) |
| 계정당 시간당 제출 수 상한 | 10건 (`RATE_LIMIT_PER_HOUR`) |
| 마크다운 지원 | 지원함 (`markdown-to-jsx`, `MarkdownBody.tsx`) |
| 위키 전용 문법 | 각주 `[* 내용]`, 문서 링크 `[[문서명]]` (`src/lib/wikiMarkup.ts`) |

**각주 문법을 한 번 바꿨고 운영 데이터를 이관했다 (2026-09-03).** 처음에는 글 아래에
정의를 모으는 방식(`[^가]` + `[^가]: 내용`)이었으나 `[* 내용]`으로 바꿨다. 이유는
`WIKI_MODEL.md`의 "주석은 내용을 그 자리에 적는다"에 적었다.

이관은 운영 D1에서 아래 한 번으로 끝냈다. 닫는 `]`는 그대로 쓰이므로 여는 쪽만 바꾼다.

```sql
UPDATE wiki_docs     SET general = REPLACE(general, '[^', '[* ') WHERE general LIKE '%[^%';
UPDATE wiki_sections SET body    = REPLACE(body,    '[^', '[* ') WHERE body    LIKE '%[^%';
UPDATE wiki_edits    SET body    = REPLACE(body,    '[^', '[* ') WHERE body    LIKE '%[^%';
```

6행(문서 1 + 편집 이력 5)이 바뀌었고 옛 문법은 0행이 남았다. **편집 이력까지 함께 바꾼
것은 의도한 선택**이다 — 시험 삼아 쓴 글이라 기록 보존 가치보다 역사 화면이 깨져
보이지 않는 쪽이 낫다고 판단했다. 실제 기여가 쌓인 뒤라면 이 판단은 달라져야 한다.

**시드 이관분 재이관은 하지 않았다.** 옛 Tip 제목이 본문 앞 줄에 평문으로 남아 있는
문서들은 마크다운 제목 문법(`#`)으로 바꾸지 않아도 그대로 문단으로 정상 렌더된다 —
필요하면 나중에 별도 스크립트로 정리해도 되는 선택 사항이지 4단계를 막는 일은 아니었다.

### 4.3 알려진 위험 — 220ms 전환

[`src/data/selection.ts`](../src/data/selection.ts)는 분류 전체(약 23KB, 배정 185건)를
직렬화해 첫 응답에 실어 보낸다. 포지션·카테고리 전환마다 서버를 왕복하면
`DESIGN_BLUEPRINT.md`가 규정한 **220ms 전환을 지킬 수 없기 때문이다.**

분류를 D1로 옮기면 이 데이터를 매 요청 조회해야 한다. 그대로 하면 첫 응답이 느려진다.

**이전 전후로 전환 시간을 실측해 비교할 것.** 느려지면 분류 조회 결과를 캐시한다.
분류는 관리자가 가끔 바꾸는 데이터라 캐시 적중률이 높고, 무효화 시점도 명확하다
(관리자가 저장할 때).

**어떤 기준으로 배정할지는 여전히 미정이다** (PRD 15 미결정 1번). 관리자 화면은 갱신
*수단*을 제공할 뿐, 아리를 `mage`에 둘지 판단해 주지 않는다. 현재 분류는
`taxonomy.ts`에 담긴 초기 운영 분류이며 그 근거는 `archive/plan1.txt`의 미드 세 카테고리뿐이다.

## 5. 운영하면서 알아야 할 것

### 5.1 `dev`와 `build`를 동시에 돌리지 말 것

둘 다 같은 `.next` 디렉터리를 쓴다. dev 서버를 켠 채 `npm run build`를 돌리면 dev 서버가
빈 페이지나 500을 뱉기 시작한다. 이 경우 **코드 문제가 아니다.** dev 서버를 끄고
`.next`를 지운 뒤 다시 켜면 된다.

```bash
rm -rf .next && npm run dev
```

### 5.2 패치 갱신

**롤 패치가 나올 때마다 돌린다.** 패치는 2주 간격(2026년 24회)이고 수요일이나 목요일에
나온다. 미국 휴일(6월 말~7월 초)과 연말 휴식기에만 3주가 벌어진다. 책임자는 운영자다
(PRD 8장 "데이터 갱신").

```bash
DDRAGON_PATCH=16.18.1 npm run data:sync   # 챔피언·스킬 다시 내려받기
npx tsx scripts/check-taxonomy.ts          # 이름이 깨지지 않았는지 점검
npm run build                              # 생성 파일이 빌드를 깨지 않는지
npm run cf:deploy                          # 갱신은 배포해야 반영된다
```

**코드 배포가 있어야 반영된다.** 챔피언·스킬 데이터는 D1이 아니라 저장소의 생성
파일(`src/data/generated/`)에 있으므로, 내려받기만 하고 배포하지 않으면 운영에는
옛 수치가 그대로 남는다.

패치 버전과 갱신 시각은 `src/data/generated/champions.json`에 저장되고 사이트 하단에
표시된다. 갱신이 늦어도 사이트는 멈추지 않는다 — 읽는 사람이 지금 보는 수치가 언제
것인지 하단에서 확인할 수 있다.

신규 챔피언이 나오면 `taxonomy.ts`에 직접 배정해야 목록에 나온다.

### 5.3 챔피언 분류 갱신

> **이 절은 관리자 화면이 생기면 바뀐다.** 분류는 D1로 옮겨가고 `taxonomy.ts`는 초기
> 이관 자료로만 남는다 (4장). 아래는 그때까지의 방식이다.

포지션·카테고리와 챔피언 명단은 [`src/data/taxonomy.ts`](../src/data/taxonomy.ts)
**한 곳에서만** 관리한다. 화면 코드에 챔피언을 개별로 고정하지 않는다 (PRD 5.1).

- 이름은 Data Dragon `ko_KR` 표기와 **정확히** 일치해야 한다. `리 신`, `트위스티드 페이트`,
  `아우렐리온 솔`, `문도 박사`처럼 띄어쓰기가 있는 이름을 조심할 것.
- 틀리면 앱이 뜰 때 오류로 잡히고, `check-taxonomy.ts`가 어떤 이름인지 알려 준다.
- 한 챔피언이 여러 포지션에 속할 수 있지만 **같은 포지션 안에서는 카테고리 하나뿐**이다.
  점검 스크립트가 중복도 잡는다.
- 분류에 없는 조합(`/matchup/mid/leesin` 같은)은 404가 된다. 의도된 동작이다 (FR-07).

### 5.5 모바일 헤더 메뉴가 가로로 넘친다

360px에서 메뉴 다섯 개(`상대법 / 전적 / 통계 / 티어표 / 강의`)의 폭이 254px인데
로고와 마이페이지 아바타를 빼면 172px만 남는다. 세 개 반만 보이고 나머지는 가로 스크롤이다.
오른쪽 끝을 흐리게 처리해 더 있다는 것은 알 수 있게 했다.

글자와 여백을 최대로 줄여도 82px이 모자라므로, 제대로 풀려면 둘 중 하나가 필요하다.

1. 모바일에서 햄버거 메뉴로 전환한다 (블루프린트에 모바일 헤더 규격이 없어 새로 정해야 함)
2. 모바일 헤더에서는 `강의`처럼 우선순위가 낮은 항목을 빼고 마이페이지 안으로 옮긴다

지금은 스크롤로 모든 메뉴에 닿을 수 있어 기능상 막힌 곳은 없다.

**2026-09-03 로그인 UI 추가로 폭이 더 줄었다.** `마이페이지` 오른쪽에 로그인 상태
표시(`AuthStatus`)가 붙어 `nav`가 쓸 수 있는 폭이 조금 더 줄었다. 텍스트 하나(`로그인`)
또는 이름(말줄임)+`로그아웃`만 두어 최소화했지만, 위 문제를 새로 만들지는 않되 악화는
시킨다. 햄버거 메뉴 전환(위 1번)을 하게 되면 이 요소도 같이 옮길 것.

### 5.6 브라우저 저장소 키 — 더 이상 쓰지 않는다

옛 Tip 게시판이 쓰던 키다. 위키 전환 2단계에서 `tipStore.ts`와 함께 걷어냈으므로 앱은
이제 아무것도 읽고 쓰지 않는다. **이전에 사이트를 방문한 브라우저에는 값이 남아 있다.**

```
kkaenam.tips.v1     내가 쓴 Tip
kkaenam.votes.v1    좋아요 · 싫어요
kkaenam.user.v1     로컬 데모 계정
```

남은 값은 동작에 영향을 주지 않지만, 정리하려면 개발자 도구에서 삭제하면 된다.
3단계에서 로그인을 붙일 때 세션 키가 새로 생기며 이 키들과는 무관하다.

### 5.7 D1 데이터베이스

상대법 저장소는 Cloudflare D1 `kkaenam-gg` (APAC)이다.

```bash
npx wrangler d1 migrations apply kkaenam-gg --local    # 로컬 스키마
npx wrangler d1 migrations apply kkaenam-gg --remote   # 운영 스키마
npx wrangler d1 execute kkaenam-gg --remote --command "SELECT COUNT(*) FROM wiki_docs;"
```

**새 마이그레이션 번호는 로컬 파일이 아니라 `origin/main`을 보고 정한다.** 로컬이 뒤처진
채로 다음 번호를 붙이면 같은 번호가 두 벌 생긴다. 실제로 2026-09-06에 알림 마이그레이션을
0008로 만들었다가 `origin/main`에 이미 `0008_wiki_links.sql`이 있는 것을 보고 0009로
옮겼다. wrangler는 번호가 아니라 **파일 이름**으로 적용 여부를 판정해서 둘 다 적용되지만,
그때부터 적용 순서와 파일 순서가 어긋난다.

`0009_notification_read_marker.sql`(알림 읽음 표시)은 로컬·운영 모두 적용했다
(2026-09-06). 헤더의 종을 그리는 질의가 이 열을 읽고 **헤더는 사이트 전체에 얹혀
있으므로**, 이 계열의 마이그레이션은 코드를 배포하기 전에 원격에 먼저 넣어야 한다.
순서가 뒤바뀌면 로그인한 사람에게 모든 화면이 깨진다.

**운영 데이터를 손으로 고친 기록.** 2026-09-06, 분류 문서 세 개의 `분류:` 접두사를
뗐다 (`분류:라인전` → `라인전` 등). 위계가 문서에서 나오게 된 뒤로 접두사는 아무 일도
하지 않는데(부모 키는 접두사를 뗐다 다시 붙여 짓는다), 화면과 주소에만 남아 있었다.
`wiki_links`는 건드리지 않았다 — 본문의 `[[분류:라인전]]` 태그는 문서 이름과 무관하게
같은 키에 닿는다. 스키마 변경이 아니므로 마이그레이션으로 만들지 않았고, 되돌릴 때
쓸 원래 값은 이 문단이 기록이다: `doc-a-35df…` = 라인전, `doc-a-52dc…` = 라인관리,
`doc-a-b1df…` = 딜교환.

**생성된 시드 SQL을 `migrations/`에 두지 말 것.** wrangler가 그 디렉터리의 `.sql`을 전부
마이그레이션으로 취급해 나중에 `migrations apply`를 돌릴 때 시드가 다시 실행된다.
`seeds/`에 두는 이유가 이것이다.
