## 1. 생각

티어의 정답을 다른 사이트에서 가져오면 그 사이트의 복사본이 된다. ABOUTLOL은 정답을
**라이엇 밸런스 팀이 실제로 내린 판단**에서 가져온다. 패치노트의 너프는 "이 챔피언이 지나치게
강했다", 버프는 "지나치게 약했다"는 사후 판정이다. 그 판정을 직전 패치의 지표로 설명하는
가중치를 학습하면, 그 가중치로 만든 점수가 곧 "라이엇이 보기에 얼마나 강한가"가 된다.

라이엇은 승률만 보지 않는다. 장인 챔피언의 높은 승률은 깎아 보고(너프하지 않음), 대회 챔피언의
낮은 솔로랭크 승률은 덮어 본다(버프하지 않음). 이 판단이 학습 자료에 들어 있으므로, 같은
구조의 항을 모델에 넣으면 가중치로 드러난다.

## 2. 식

```text
y = w₁x₁ + w₂x₂ + … + w₁₃x₁₃ + b          (xᵢ = 표준화한 강함 지표)
```

학습은 순서형 로지스틱 회귀(cumulative logit)로 한다. 라벨은 버프(0) / 유지·조정(1) / 너프(2).

```text
s = Σ wᵢ·zᵢ      (강함 + 통제 지표 모두)
P(버프)          = σ(θ₁ − s)
P(버프 또는 유지) = σ(θ₂ − s)
b = −(θ₁ + θ₂)/2
```

- **등급 경계가 라이엇의 판단 경계에 묶인다.** h = (θ₂ − θ₁)/2일 때 y ≥ h는 "라이엇이 너프할
  수준"이라 **S**, y ≤ −h는 "버프할 수준"이라 **5**, 그 사이를 넷으로 고르게 나눠 1~4다
  (`score.ts`의 `tierCuts`). 임의의 0~100 눈금을 만들지 않는다 (PRD 3.1).
- **정규화는 사전 가중치 쪽으로 당긴다.** `λ/2·Σ(wᵢ − priorᵢ)²`. 라벨이 적을 때는 근거 있는
  사전값을 유지하고 자료가 쌓이면 자료가 이긴다. 값이 하나도 관측되지 않은 지표는 사전값 그대로다.
- **결측은 0이 아니다.** 표준화 평균(기여 0)으로 두고 상태를 `데이터 부족`으로 표시한다.
  승률 표본이 100판 미만이면 점수·등급은 null(산출 불가)이다.

## 3. 지표 17개

강함(strength) 13개는 티어 점수에 들어간다. 통제(control) 4개는 **학습에만** 쓴다 — 라이엇이
*언제* 손대는가(직전에 너프했으면 결과를 기다린다)를 흡수해 강함 가중치가 패치 일정에
오염되지 않게 한다. "방금 너프됐다"는 이유로 티어를 깎으면 강함이 아니라 일정을 보여 주게 된다.

높아도 너프 근거로 보지 않는다", "대회 챔피언은 승률이 낮아도 버프 근거로 보지 않는다"를
가중치 하나씩으로 표현한다. 부호와 크기는 학습이 정하고, 사전값은 그 방향만 미리 둔 것이다.

사전값은 라이엇 밸런스 프레임워크(2019·2020, [research/tier-basis-2026-09-26.md](./research/tier-basis-2026-09-26.md))가
승률과 밴율을 1차 신호로, 대회에서는 픽+밴을 본다고 밝힌 데 따른 순서다. 크기 자체는 근거가 아니라
출발점이며 학습 자료가 생기면 덮인다.

## 4. 라벨 — 공식 패치노트

- 범위: **25.S1.1 ~ 26.19, 43개 패치, 챔피언 변경 676건, 166명** (`data/tier-model/patch-changes.json`)
- 추출: 영문 공식 패치노트의 소환사의 협곡 `Champions` 절과 `Mid-Patch Updates` 절. 아레나·칼바람 절은 뺀다.
  "이번 패치의 X 변경은 오류로 적용되지 않았다"는 취소 공지(26.6 카시오페아)는 그 패치 라벨을 지운다.
- 판정: 개발자 의도 문장의 단서 + `이전 ⇒ 이후` 수치 방향(재사용 대기시간·소모값은 작을수록 버프).
  둘이 엇갈리거나 약하면 사람이 판정한다.
  - 자동 463건 · 수동 213건 (`label-overrides.json`, 의도 문장을 읽고 판정)
  - 자동 판정 무작위 표본 검증: 40건 중 39건, 재표본 30건 중 28건 일치. 불일치는 모두 "빌드 방향
    전환"처럼 해석이 갈리는 경계 사례였다.
  - 힘 이동·버그 수정·체계 보정은 `adjust`(유지)로 둔다. 방향이 없는 변경이다.
- 시간 맞추기 (`dataset.ts`): 스냅숏 N의 라벨 = **N 도중의 패치 중간 업데이트 + N+1 본문**.
  N 본문은 N이 시작될 때 이미 들어간 변경이라 라벨이 아니라 입력(최근 너프·버프)이다.
  라벨에 쓰는 변경이 입력으로 새지 않는지 `check-tier-model.ts`가 검사한다.
- 시즌 시작 패치(25.S1.1, 26.1)는 라벨에서 뺀다. 치명타 체계 변경 같은 **예측성 보정**을 대량으로
  넣는 패치라 "직전에 강했다"는 판단이 아니다.

### 라벨의 한계

1. 라이엇은 전 서버·전 티어·대회 자료를 보고, ABOUTLOL 지표는 KR 솔로랭크 구간 표본이다. 같은 것을 보지 않는다 (구간 표본 도입으로 티어 범위의 차이는 줄었다).
2. 라벨은 챔피언 단위다. 학습 행은 챔피언마다 가장 많이 플레이된 포지션 하나만 쓴다.
   "정글만 너프" 같은 포지션 한정 변경은 그 포지션이 주 포지션이 아니면 잡음이 된다.
3. 라이엇은 강한 챔피언을 **전부** 고치지 않는다(패치당 평균 버프 7.4, 너프 6.8). 손대지 않은
   챔피언 중에도 강한 챔피언이 섞여 있어 "유지" 라벨에 잡음이 있다. 그래서 평가는 정확도보다
   순위 지표(AUC, Precision@k)를 본다.
4. 라벨은 행동이다. 통제 지표로 행동 습관을 흡수하지만 완전하지 않다.

## 5. 학습과 평가

```bash
npm run tier:labels       # 패치노트 → 라벨 (원문 캐시는 .cache/, 커밋하지 않음)
npm run tier:snapshots    # 로컬 D1 구간 표본 → data/tier-model/snapshots/<패치>/<구간>.json
npm run tier:train        # 학습·평가 → src/data/generated/tier-model.json
npx tsx scripts/check-tier-model.ts
```

- **시간 순 검증**: 패치 i는 i보다 앞선 패치로만 학습하고 맞힌다. 앞선 패치 4개 이상부터 잰다.
- 지표: 로그 손실(라벨 비율만 아는 기준선보다 낮아야 함), 너프·버프 AUC, 패치별 Precision@k
  (그 패치 너프 수 k만큼 상위 k를 골랐을 때 실제 너프 비율).
- 합성 자료 검사(`check-tier-model.ts`): 정답 가중치를 아는 자료 3,600행에서 6개 가중치의 부호와
  상대 비율을 복원하고, 시간 순 검증 AUC 0.98 이상. 합성 자료는 파일로 남기지 않는다.

## 6. 현재 상태와 다음 단계

**학습 행 0.** 라벨은 43개 패치에 있지만, 그 패치들의 지표 스냅숏이 없다. 구간 표본 수집은 기본
꺼짐이고, 로컬 개발 키는 만료(401) 상태다. 그래서 `tier-model.json`은 `status: "prior-only"`이고
`tier_scores`는 비어 있어 화면의 구간 보드는 모두 "준비 중"이다.

| 필요한 것 | 방법 | 막힌 이유 |
| --- | --- | --- |
| 구간 표본 (현재 패치) | `TIER_SAMPLE_REQUESTS`로 켜기 (8장) | Production 키. 구간당 패치마다 10만 판 안팎이 목표 |
| 과거 패치 지표 스냅숏 | 구간 표본에 지난 패치 백필 추가 (match-v5는 과거 경기 조회 가능) | 미구현. Production 키 필요 |
| 앞으로의 스냅숏 | 패치마다 `tier:snapshots` | 패치당 한 행씩 쌓여 의미 있는 검증까지 수개월 |
| 대회 픽밴률 | Leaguepedia Cargo API (`PicksAndBansS7`) | 비로그인 호출이 즉시 속도 제한됨. 봇 계정 필요 |
| 장인 의존도·조작 난이도·선픽 적합도 | 운영자 입력 (PRD 9장) → `operator-metrics.json` | 운영 메뉴 미구현 |

공개 전환 조건(PRD 11장, `board.ts`의 `publishGate`): 시간 순 검증에서 로그 손실이 기준선보다 낮고,
너프·버프 AUC가 모두 0.6 이상. 조건을 못 넘으면 `tier:publish`가 거부한다. 그 전에는 운영 배정 보드를 유지한다.

0017은 로컬 D1에만 적용했다. 화면 코드는 `tier_scores`가 없어도 "준비 중"으로 동작하지만,
구간 표본을 켜기 전에는 **운영 D1에 0017을 먼저 적용**해야 한다.

```bash

# wrangler.collector.jsonc env.production.vars에 "TIER_SAMPLE_REQUESTS": "40" 등을 넣고

```

## 7. PRD와의 관계

PRD v0.2는 "다음 패치 너프 확률"을 범위에서 뺐다(FR-68 취소). 이 모델은 너프 여부를
**정답 라벨로만** 쓰고, 너프 확률을 화면에 공개하지 않는다. 공개하는 것은 강함 점수와 등급뿐이다.
`P(너프)`는 학습 내부 값이다.

## 8. 티어 구간

| slug | 구간 | 래더 범위 |
| --- | --- | --- |
| `iron-silver` | 아이언 ~ 실버 | 각 디비전 I~IV |
| `gold-platinum` | 골드 ~ 플래티넘 | 각 디비전 I~IV |
| `emerald` | 에메랄드 | I~IV |
| `diamond` | 다이아몬드 | I~IV |
| `master-plus` | 마스터 이상 | 마스터·그랜드마스터·챌린저 리그 전체 |

라이엇 밸런스 프레임워크는 일반·상위·최상위 솔로랭크와 대회로 나눠 본다. 다섯 구간은 그 생각을 빌린
ABOUTLOL의 구분이며 라이엇 공식 구간이 아니다. 정의는 `src/data/brackets.ts` 한 곳에만 둔다.

### 수집 (`tierSampler.ts`)

빌드 수집기와 같은 임대·호출 간격·429 처리 안에서 별도 예산으로 돈다. 기본 예산 0 — 켜지 않으면 호출하지 않는다.

1. **래더**: 디비전 하나에서 무작위 쪽을 열어 계정 몇 명을 뽑는다. 쪽수를 모르므로 빈 쪽을 만나면
   상한(`max_page`)을 줄이고 상한 쪽이 차 있으면 늘려, 시간이 지나면 고르게 뽑힌다.
2. **기록**: 뽑힌 계정의 최근 14일 솔로랭크 경기 ID. 계정당 패치마다 최대 5경기 — 장인 한 명이 표본을 덮지 않게 한다.
3. **경기**: 경기 정보만 받는다(타임라인 없음, 경기당 호출 1회). 열 명 모두의 챔피언·포지션·승패와 밴을 남긴다.
   포지션이 빈 참가자가 있으면 픽률 분모가 어긋나므로 경기를 뺀다.

**경기의 구간 = 그 경기를 찾게 한 계정의 구간.** 열 명의 티어를 각각 조회하면 호출이 열 배가 된다.
매칭이 비슷한 실력끼리 이뤄진다는 가정이라, 구간 경계 근처의 경기에는 옆 구간 이용자가 섞인다.

### 학습과 채점

- 라벨(라이엇 판단)은 구간과 상관없이 챔피언당 하나라, 구간마다 학습하면 같은 라벨을 다섯 번 센다.
  그래서 **가중치는 다섯 구간을 합친 `all` 스냅숏으로 한 번만 학습**하고, 각 구간의 지표를 넣어 구간별 점수를 낸다.
- `all`은 다섯 구간 표본의 단순 합이다. 실제 이용자 분포로 가중하지 않았다(수집기가 구간을 고르게 돌아
  하위 구간이 인구보다 적게 들어간다). 학습용이며 화면에는 쓰지 않는다.
- 표본 목표: 구간당 패치마다 10만 판 안팎. 포지션 내 픽률 2%인 챔피언이 약 4,000판(승률 ±1.5%p)이 된다.
  마스터 이상은 인구가 적어 모자랄 수 있다 — 실측 후 최근 2패치 합산을 검토한다.

### 공개와 화면

```bash
npm run builds:sync -- --tier-requests 40 --cycles 20   # 로컬 표본 (Production/개발 키)
npm run tier:snapshots                                  # data/tier-model/snapshots/<패치>/<구간>.json
npm run tier:train
npm run tier:publish [-- --remote]                      # 검증 통과 모델만 tier_scores에
npm run tier:publish -- --unvalidated                   # 로컬 화면 확인용 (운영 불가)
npm run tier:publish -- --clear [--remote]              # 공개 점수 내리기
```

라인 화면(`/`)의 티어 목록 위에 `운영 배정 / 아이언~실버 / 골드~플래 / 에메랄드 / 다이아 / 마스터+` 선택이 있다.
주소의 `?bracket=`이 상태이고, 없으면 운영 배정 보드다. 다섯 구간 결과를 첫 응답에 함께 실어
구간·라인을 바꿀 때 서버를 다시 부르지 않는다. 공개 점수가 없는 구간은 "준비 중"을 보여 준다.
표본 부족으로 등급을 못 낸 챔피언은 맨 아래 묶음이며, 그 승률은 숨긴다(몇십 판의 우연이라).

**기본 구간은 아직 정하지 않았다** (PRD 4.1 — 출시 전 결정). 후보: 이용자가 가장 많은 구간, 또는
Riot ID로 조회한 이용자의 현재 티어 구간(개인화, PRD 5장).
